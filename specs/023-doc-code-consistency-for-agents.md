# Fix four bugs, then measure agent turns

**The answer: build almost nothing new.** Four verified bugs are currently making Holusight's doc-code consistency layer actively worse than having no layer, and they total under a day of work. After that, the only two things worth building are a mechanical bidirectional inventory check (every name in a doc resolves; every file on disk is accounted for in the structure docs) and symbol-level structural queries over the Graphify edges you already commit and currently throw away. Both are mechanical, model-free, and one of them is already authorized by an accepted ADR in this repo. The convergence that makes this confident is that two independent internal audits found your broken mechanisms were each reaching for exactly the technique that two independent external surveys identify as the best-evidenced one: **narrow, name-level, mechanically-resolved checking, never a smarter judge of prose.** The uncomfortable half is that the largest study of repository context files found they do not generally improve agent success and add over 20% cost, with repository overviews specifically unhelpful ([arXiv 2602.11988](https://arxiv.org/html/2602.11988v2)). Your thesis survives in its consistency half, not its documentation-volume half: incorrect comments substantially degrade model performance while missing ones barely matter ([arXiv 2512.16790](https://arxiv.org/html/2512.16790v1)), so **removing a wrong doc is worth more than adding a right one.** Finally, your current harness optimizes a metric that correlates with what you care about at Spearman ρ = 0.129 to 0.237 ([Agent Retrieval Bench, arXiv 2607.24882](https://arxiv.org/html/2607.24882v1)), and the fix is a cheap published design you can run locally on your own repo history.

## Two independent audits and two independent surveys converged on the same sentence

This is the spine of the finding, and it is not four parallel observations. The internal audits found that your two highest-value mechanisms are both reaching for name-level mechanical resolution and both failing for mundane reasons. `extract_exact_references` resolves path tokens against the raw filesystem via `_resolve_candidate` (`src/holusight/consistency.py:341-354`) while `discover_artifacts` delegates to `walk_repo_files`, which drops every dot-directory (`src/holusight/indexer.py:68-84`). The two enumerations disagree, so edges are created into `.claude/` files that are absent from the 218-row artifacts table, `_artifact_changed` hits its `if not row: return True` branch forever, and five concepts report drift permanently. The same asymmetry silently kills two `classify_artifact` branches written specifically to recognize `.claude/rules/*.md` as canonical governance. Meanwhile the structural provider never reads a single graph edge: `structural_provider` (`src/holusight/axi_providers.py:227-307`) builds `haystack = path.lower() + " " + " ".join(node_ids).lower()` and substring-matches query tokens. It is a fuzzy filename grep wearing the word "structural," and it is the third independent re-implementation of that same trick (`tests/eval_baselines.py:221-300` is the others).

The external surveys then say, from an entirely different direction, that name-level mechanical resolution is precisely the technique with the best evidence, and that every high-precision result in the literature got there by narrowing what it claims to check rather than by getting smarter. @tComment hit roughly **98% precision** by narrowing to a structured Javadoc tag convention, and its authors attribute that to the structure rather than the technique, noting free-form analysis reached 97-100% accuracy *without* NLP ([@tComment](https://mir.cs.illinois.edu/marinov/publications/TanETAL12tComment.pdf)). The same rule-based approach applied to a general corpus falls to F1 around 66.7 with accuracy near 50. DocPrism reduced the flag rate from **over 90% to 17%** at precision 0.63 by asking only about incorrectness and discarding incompleteness ([arXiv 2511.00215](https://arxiv.org/abs/2511.00215)). CASCADE reached precision 0.88 by requiring an executable discriminator, but at recall 0.21, and **its precision collapses to 0.39 purely by moving from a 50/50 to a 10/90 class balance** ([arXiv 2604.19400](https://arxiv.org/html/2604.19400)). Your nightly repo-scale imbalance is far more extreme than 10/90, which is the decisive argument against ever putting an LLM judge on this surface.

Your existing regex-on-named-invariants approach is already an instance of the winning pattern. The correct next move is to narrow further and resolve symbols instead of matching strings, which is item 6, not to widen coverage with a model.

## Documentation does not help agents; documentation that lies hurts them

Say the uncomfortable part plainly. The largest study of repository context files found they **do not generally improve task success rates while increasing inference cost by over 20% on average**, holding across LLMs, agents, and both LLM-generated and developer-written files, and found that repository overviews, the thing model providers recommend, were specifically not helpful ([arXiv 2602.11988](https://arxiv.org/html/2602.11988v2)). LLM-generated files caused drops in 5 of 8 settings; developer-provided files gained **+2.4% on average at p = 0.21**, which is to say not significant, and helped every agent except Claude Code. The decisive ablation: when researchers removed all documentation from the repositories, LLM-generated context files **became helpful, at +2.7%**, which means `/init`-style files mostly pre-cache what the agent would have found itself. An independent replication reached the same null against a working positive control: when the source is present, neither compact documentation nor retrieved context beats the issue alone, and only when the source file is *withheld* does an optimized description lift mean test-pass fraction from **0.08 to 0.71** ([arXiv 2609.31587](https://arxiv.org/html/2609.31587v1)). Documentation acts as a code substitute, not a supplement.

That kills "more docs make agents efficient." It does not touch "docs that do not lie." **Incorrect comments substantially degrade model performance while missing or incomplete comments have relatively minor impact** ([arXiv 2512.16790](https://arxiv.org/html/2512.16790v1)), and CodeCrash showed GPT-4o correctly trace execution to the right output, then adopt a false comment and contradict its own reasoning, never mentioning the comment in its trace ([arXiv 2504.14119](https://arxiv.org/pdf/2504.14119)). The influence is implicit, which means an agent will not tell you it was misled. That asymmetry is the actionable form of your thesis: the expected value of deleting or fixing one wrong statement exceeds the expected value of adding a right one. It is also an argument against your own instruction surface, which currently loads the same six-bullet graphify block three times and points all three copies at a path that does not exist on this machine.

Two structural facts reinforce the deletion bias. Code and comments do not co-evolve in roughly **80%** of cases across 1,500 projects with 500 manually analyzed commits ([Wen et al., ICPC 2019](https://www.inf.usi.ch/lanza/Downloads/Wen2019a.pdf)), so any control relying on an author or agent noticing is measured to fail four times in five; only a mechanical check forces it. And Google, which built internal doc freshness tooling, reports its durable wins were co-location, named ownership and CI-integrated checking, with roughly **90% of GooWiki documents having no views or updates in the months before deprecation** ([SWE at Google ch.10](https://abseil.io/resources/swe-book/html/ch10.html)). Freshness dates measure attention, not accuracy, and an agent can bump a date without reading anything.

## Your harness optimizes a metric that correlates at ρ = 0.13 to 0.24

Retrieval ranking metrics correlate weakly with agent outcomes. Agent Retrieval Bench measured Spearman **ρ = 0.129 to 0.237** between initial-context quality and agent outcomes across scaffolds at n = 287, and concluded context-acquisition metrics should be used as "a diagnostic proxy, not a scalar causal estimate" ([arXiv 2607.24882](https://arxiv.org/html/2607.24882v1)). The Recall Trap is the cleanest demonstration of the divergence: gold-file recall **fell** from 0.878 to 0.806 while resolve rate **rose 7.6 points** from 39.2% to 46.8% at n = 500, McNemar p = 0.0003 ([arXiv 2608.14838](https://arxiv.org/abs/2608.14838)). CodeGrep found that below a precision threshold retrieval actively hurts, with BM25 at file-precision 0.375 costing 0.6 points of resolve rate and inflating tokens 21% on SWE-bench Verified, and that the marginal harm of a false positive is comparable to the marginal benefit of a true positive ([arXiv 2608.05886](https://arxiv.org/pdf/2608.05886)).

Applied to your numbers: the +0.224 MRR you record for AST chunking in `ARCHITECTURE.md` (0.599 to 0.823) is far larger than anything published. cAST's own paper claims +4.3 Recall@5 points ([arXiv 2506.15655](https://arxiv.org/html/2506.15655v1)), and a much larger controlled study across **864 settings** found sliding-window chunking slightly **beat** cAST on both RepoEval (46.23% vs 45.93% API-level EM) and CrossCodeEval (28.40% vs 28.19%), concluding structure-aware chunking does not outperform on quality or cost ([arXiv 2605.04763](https://arxiv.org/html/2605.04763)). On a 96-file, 20-query harness, small-sample variance or confounding is the more plausible explanation than AST chunking being unusually good on your repo. Your own downstream number (93.0 to 93.8, n = 9) is consistent with near-zero and cannot attribute the 0.8 points to any one component.

**The cheap eval design, concretely.** Take 30 to 50 tasks from your own repositories' history where a test exists and passes after the fix and fails before it. Run the same agent and model paired, with the Holusight context pack on and off, from the pre-fix commit, with a fixed and generous step budget. Primary endpoint is test-based pass or fail. Apply **McNemar's exact test** on the paired binary outcome. Include a **positive control** that injects the oracle gold files, to prove your harness can detect a real effect at all. The practical detail that makes this affordable: **process metrics move detectably at small n where resolve rate does not.** Agent Retrieval Bench's 45-sample single-run seed pilot detected first-gold-hit moving from step 3 to step 1 and tool calls from 5.4 to 3.7, while File F1 moved 0.3222 to 0.3967 against an oracle ceiling of 0.6337 ([arXiv 2607.24882](https://arxiv.org/html/2607.24882v1)). So measure **tool calls to first gold-file touch, total input tokens, and turns** as primary, and treat pass rate as secondary. Turn count is also the metric with a credible economic story: the one controlled structural-index comparison reports **$2.30 vs $2.92 per solved task, 10.1k vs 14.0k mean tokens, 28.3 vs 36.0 mean turns, both p < 0.0001** ([arXiv 2606.22417](https://arxiv.org/pdf/2606.22417)), and RepoGraph measured turns falling 21.47 to 19.12 ([arXiv 2410.14684](https://arxiv.org/html/2410.14684v1)). Two caveats on that first paper: I am reporting only its cost, token and turn figures, because an accuracy figure attributed to it could not be corroborated and is probably a PDF-extraction artifact.

Two more evidence-quality distinctions worth preserving. The 26.2% hit rate your graphify baseline currently reports is **invalid**, not merely coarse: 61 of 85 ground-truth paths do not exist, the entire 26.2% comes from the doc and test families whose paths survived the rename, and `symbol_reference` scoring 0 of 10 is **not** evidence that structure failed, because all ten of those queries are ungradeable. And Cursor's widely cited ~12.5% accuracy gain from semantic search is vendor-originated and reached me only through a secondary write-up ([Towards Data Science](https://towardsdatascience.com/how-cursor-actually-indexes-your-codebase/)); the durable, primary fact is that Cursor's current docs describe a local grep-based retrieval path with no stored codebase embeddings ([Cursor docs](https://cursor.com/docs/context/codebase-indexing)).

**Nobody has measured whether automated doc-code consistency checking improves agent outcomes.** The harm of stale docs is established; the benefit of a tool that finds them is not. No study measures agent task success as a function of documentation accuracy, and given that models adopt false comments implicitly without citing them, it is not even obvious that handing an agent a "this doc is stale" warning changes its behavior. You would be first. That is both the strongest reason to run item 10 and the honest risk to the whole project: if the paired eval shows no movement in turns-to-gold, the consistency layer's value is unproven and the correct response is to keep only the cheap mechanical checks.

Where this diverges from prior thinking in this repo: ADR-0019 already marked specs 011 and 012 reference-only and explicitly did not authorize the 96-task paid suite, and PR #27 and PR #32 were both closed as infrastructure-only. Nothing above asks to resume that. Spec 012's experiment ladder starts at 12 to 20 tasks with public corpora and climbs through a "first authorized one-night run"; I recommend skipping that ladder entirely and running 30 to 50 tasks **from your own repository history** with executable tests, because contamination and validity concerns make public SWE-bench-era sets weak 2026 evidence and because your own history is free, uncontaminated, and exactly your workload. Spec 012 also freezes ten task families and a full promotion-gate apparatus; that is the wrong shape for a repo where promotion is denied by accepted decision anyway. Two open questions spec 012 named are now partly answered by the external evidence. Spec 012 line 473 asked whether Graphify's incremental value is real and framed Holusight vs Graphify vs Holusight+Graphify as the decisive comparison: Agent Retrieval Bench measured exactly that fusion, with RRF over embedding plus repo-map improving MRR from 0.2336 to **0.2713** and Recall@20 from 0.7070 to **0.7331**, and the repo-map arm alone producing the best budgeted-context yield of any method tested at **0.3788**, with structural signal winning causal-indirect queries and embeddings winning semantic-direct ones. That supports fusion and, more usefully, supports **routing by query type** rather than blending. Spec 012's insistence on cost per correct outcome over nDCG is vindicated and should be kept.

## Conclusion

The report's real finding is that Holusight's problem is not missing capability, it is that four unremarkable bugs have hollowed out the capability it already shipped, and the project's own specification has drifted inside the document that defines the consistency engine: spec 013 states a corpus of "~127 files" while the live count is **218**, a genuine doc-code drift found by hand because no registered claim covers corpus size. The engine cannot currently keep its own tracked structural graph honest either. That is not an indictment of the thesis; it is the strongest available evidence for the narrow version of it. A repository maintained by agents accumulates exactly this class of silent, mechanical, name-level falsehood, and every one of the four bugs would have been caught on day one by the bidirectional inventory check that item 5 proposes.

The strategic reframe worth carrying forward: your differentiator is not retrieval quality. It is that you hold a semantic index and an AST graph over the same tracked corpus, plus the only checker that knows when the two disagree with the prose. The literature says structural plus semantic fusion is the best measured combination and that wrong docs are measurably harmful while missing docs are not. Those two facts describe something worth building. "Better retrieval" and "more documentation" do not, and the evidence is now clear enough that continuing to optimize MRR on an 85-query fixture whose ground truth is 72% dead is the one thing that would waste the most time for the least return.
