# External Prior Art on Detecting and Preventing Documentation-Code Drift

Scope note for the report writer: the client already has (a) content-hash diffing that detects co-change but cannot judge agreement, and (b) regex extraction of a handful of named numeric invariants. Everything below is assessed against that baseline, for a single mid-size Python repo maintained largely by AI agents. Where a technique is widely recommended but weakly evidenced I say so explicitly.

A vocabulary distinction used throughout, because it is the load-bearing one:

- **Mechanical verification** - the check either passes or fails by execution or by exact symbol/graph lookup. Zero triage cost, trustworthy, but only covers claims expressible in the checker's language.
- **Heuristic suspicion** - the check produces a ranked list of "this looks stale." Needs a human (or an agent with authority) to adjudicate. Its value is entirely determined by precision at the top of the list, and its cost is entirely triage.

## Q1. Executable documentation: how effective is "make the doc a test"?

### Takeaway
Executable documentation is the only technique in this survey that gives genuine mechanical proof, and it is cheap to adopt in Python (Sybil, pytest-codeblock, xdoctest). Its hard ceiling is that it can only prove claims about *observable behavior of small examples* - it cannot prove a prose claim about architecture, rationale, layering, or "why." Rust's version is stronger than Python's not because the idea is unique (Python's `doctest` was the inspiration) but because Rust compiles and type-checks every example by default; that default carries real build-time cost and does not transfer to a dynamic language.

### Cited Findings
- Rust doctests are not run by the normal `#[test]` harness; `rustdoc --test` runs them, injecting boilerplate so each example becomes a compilable, runnable program. This is why `cargo test --all-targets` surprisingly skips them - [rust-lang/cargo #6669](https://github.com/rust-lang/cargo/issues/6669); [rust-lang/cargo #2684](https://github.com/rust-lang/cargo/issues/2684)
- Rust's doctests require a linkable library artifact: they do not work for `bin` targets even with `doctest = true` set explicitly, and do not run for `cdylib` and other non-rlib crate types - [rust-lang/cargo #5477](https://github.com/rust-lang/cargo/issues/5477); [rust-lang/cargo #4717](https://github.com/rust-lang/cargo/issues/4717)
- Doctests are skipped entirely when the compile target differs from the host, i.e. cross-compilation silently loses the guarantee - [rust-lang/cargo #6460](https://github.com/rust-lang/cargo/issues/6460)
- Rust's doctest model has a real cost problem: Cargo compiles and links a separate executable per doctest, and some larger projects reportedly adopt "no doctests" policies because of compilation/link time blowup; coverage tooling (`cargo-llvm-cov`) has only limited doctest support - [Swatinem, "Rustdoc doctests need fixing"](https://swatinem.de/blog/fix-rustdoc/)
- The "treat any fenced/indented block as a test" default produces false failures on generated code: `cargo test` tries to execute English prose from bindgen-generated headers as doctests, and the `#![doc(test(ignore))]` escape hatch is a crate-level directive that does not compose with `include!`d files - [rust-lang/cargo #7252](https://github.com/rust-lang/cargo/issues/7252)
- `#[cfg(doctest)]` (stable since Rust 1.40) lets an external Markdown file be imported as a doc comment so its code blocks get tested, existing only during doctest runs - [Guillaume Gomez blog](https://blog.guillaume-gomez.fr/articles/2020-03-07+cfg(doctest)+is+stable+and+you+should+use+it)
- Python's own pytest documentation recommends going beyond built-in doctest support: builtin pytest doctest handles only doctest blocks, and for broader documentation checking (doctests, `.. code-block:: python` Sphinx directives, and other examples) pytest's docs point to **Sybil**, which ships pytest integration - [pytest doctest docs](https://docs.pytest.org/en/4.6.x/doctest.html); [Sybil integration docs](https://sybil.readthedocs.io/en/latest/integration.html)
- Sybil parses examples out of code and documentation and evaluates them, hooking `pytest_collect_file` with config in a `conftest.py` in the docs source directory. Current release (10.1.0) requires Python >= 3.11, added `run_pytest()` for in-process execution of doc examples that use fixtures, and renamed `CodeBlockParser` to `PythonCodeBlockParser` - [Sybil changes](https://sybil.readthedocs.io/en/latest/changes.html); [Sybil PyPI](https://pypi.org/project/sybil/)
- **pytest-codeblock** discovers Python examples in reStructuredText and Markdown and runs them as tests. By default it collects only blocks named starting with `test_`; `test_nameless_codeblocks = true` under `[tool.pytest-codeblock]` in `pyproject.toml` opts into testing all blocks. Its `pytestrun` marker allows fixtures/classes/setup-teardown inside doc snippets, versus plain `exec()` for ordinary blocks - [pytest-codeblock docs](https://pytest-codeblock.readthedocs.io/en/latest/markdown.html); [PyPI](https://pypi.org/project/pytest-codeblock/)
- A third option, `pytest_codeblocks`, targets README blocks and supports stitching split blocks with a `pytest-codeblocks:cont` prefix - [libraries.io](https://libraries.io/pypi/pytest_codeblocks)
- `xdoctest` is a rewrite of Python's builtin doctest with a less brittle parser - [Erotemic/xdoctest](https://github.com/Erotemic/xdoctest)
- The stated payoff, in Rust's own community framing: tested examples are what "prevents the examples from becoming outdated or incorrect," and examples are less usable when import paths are hidden, which is why idiomatic doctests include their `use` statements - [rust-lang forum](https://users.rust-lang.org/t/cargo-doc-and-doctests/69194)

### Inferences
- The reason Rust's approach "has not spread more widely" is mostly mis-framed. Python (`doctest`), Go (testable examples) and Elixir (`doctest/1`) all have the mechanism. What Rust has is the *default*: doctests run as part of `cargo test` with full compilation and type checking. The sourced complaints above show that default is expensive (per-doctest link step, cross-compilation gaps, prose-as-test false failures) and that Rust itself has not fully paid down that cost. So the honest claim is: the *default-on, compiled* variant is what is rare, and the reason is build cost plus false failures on non-hand-written docs, not ignorance of the idea.
- For a Python repo the marginal step is small and mechanically sound: adopt Sybil or pytest-codeblock so that every fenced Python block in `README.md`, `ARCHITECTURE.md`, and specs is executed in CI. This converts "example drift" from undetectable to impossible. It says nothing at all about architectural prose.
- Fraction of doc content expressible this way: I found no study measuring this, but the structural argument is strong. An "executable" doc claim must be (i) about runtime behavior, (ii) reducible to a small self-contained snippet, (iii) deterministic. Claims of the form "module A owns X," "the pipeline is walk -> parse -> chunk -> embed," "we chose SQLite because," and "never write inside an indexed folder" fail (ii) or (i) entirely. In a spec/ADR-heavy repository like the client's, the executable-doc-addressable share of prose is small - it is the API-surface docs, not the architecture docs.

### Gaps
- No empirical measurement found of what fraction of documentation content is expressible as executable examples, in any language.
- No adoption statistics found (e.g. share of top PyPI packages running doctests/Sybil in CI). Go testable examples and Elixir doctests were not sourced directly in this pass; their mechanics are well known but I have no citation here, so the report should not assert numbers about them.

## Q2. Single-source-of-truth generation: when does it eliminate drift vs relocate it?

### Takeaway
Generation eliminates drift only for the *projection* it generates, and reliably relocates drift into the annotations or hand-maintained spec that feeds the generator. The OpenAPI community's own diagnosis is structural and directly transferable: drift happens because two artifacts both claim to define behavior and neither is authoritative; the fix is not a direction (spec-first vs code-first) but picking one source and validating the other against it in CI, ideally against *real runtime behavior*.

### Cited Findings
- The root cause framing: "the code and the spec both claim to define the API, neither is authoritative, so they diverge freely - you need a single source of truth," and the debate "isn't really about preference. It's about preventing the slow drift between what an API claims to do and what it actually does" - [dev.to: Spec-First API Development](https://dev.to/apikumo/spec-first-api-development-make-your-openapi-file-the-source-of-truth-4lnp); [AppMaster: OpenAPI-first vs code-first](https://appmaster.io/blog/openapi-first-vs-code-first-api-development)
- Symmetric failure modes: spec-first drifts when the spec is treated as a one-time design doc and stops being updated; code-first drifts when code changes but annotations do not, so the generated spec *looks* authoritative while status codes, required fields and edge cases have quietly moved - [AppMaster](https://appmaster.io/blog/openapi-first-vs-code-first-api-development); [Wiz Academy: API drift](https://www.wiz.io/academy/api-security/api-drift)
- "Valid is not accurate": a generated spec can be structurally valid and still misleading or incomplete, and code-first generators do not infer everything correctly, especially complex schemas and security definitions - [DocuWriter](https://www.docuwriter.ai/posts/how-to-generate-openapi-spec-from-code)
- Where drift surfaces first in practice: naming, types, and required fields - a field renamed in code but not the spec, or a boolean becoming a string because one client sends `"true"` - [Wiz Academy](https://www.wiz.io/academy/api-security/api-drift)
- Spec drift is characterized as "the most common and detectable form of API drift," occurring when production request/response schemas shift from the OpenAPI spec - [Wiz Academy](https://www.wiz.io/academy/api-security/api-drift)
- Mitigations reported to work: never hand-edit generated output; regenerate as part of the build so the spec cannot go stale; compare every API response against the spec in CI (tools named: OpenAPIValidator, Dredd) so a type/field/structure deviation blocks deployment; validate live traffic against the spec at runtime; ship spec changes in the same PR, because "teams that separate code review from contract review usually create drift again, just with better tooling" - [Wiz Academy](https://www.wiz.io/academy/api-security/api-drift); [AppMaster](https://appmaster.io/blog/openapi-first-vs-code-first-api-development)
- A "policy, not tool" point worth transferring: *which* drift fails the build should be an explicit decision - a `/health` endpoint missing from the spec is usually fine, a method mismatch on a payment route is not - [Wiz Academy](https://www.wiz.io/academy/api-security/api-drift)
- Drift is reintroduced when a spec is converted into a downstream proprietary format: an OpenAPI document ingested into a gateway's own config becomes "a snapshot that immediately begins drifting" as teams edit through the gateway UI/CLI - [Zuplo](https://zuplo.com/learning-center/openapi-first-api-gateway)

### Inferences
- Generation genuinely eliminates drift exactly when the generated artifact is *never edited* and is *regenerated unconditionally in CI with a diff check*. The diff check is the actual mechanism; generation alone is not. `sphinx-autodoc` eliminates signature drift in rendered docs because the signature is read from the live code at build time - but it eliminates nothing about the *prose* in the docstring, which is where the semantically wrong information that misleads an agent actually lives.
- The transferable design for the client's repo is the CI regeneration diff, which they already use in one place: their generated `.claude/skills/holus/SKILL.md` is produced from `axi_schema.py`, and `tests/test_axi_skill_drift.py` fails the ordinary pytest run when the two diverge. That is the correct pattern and is mechanically sound. The leverage question is how many more doc surfaces can be moved behind it.
- "Typed-config-as-canonical" is the strongest, cheapest form of this pattern for a Python repo: if a documented default is a field on a Pydantic settings object, a test can assert doc-stated default == live default without regex, and the assertion breaks loudly on rename. This is a strict upgrade over regex extraction of numeric invariants and costs about one test per invariant.
- Cost of the constraint: generation forces the canonical side to carry all the expressiveness. Doc-generation tools push authors toward reference documentation and away from narrative explanation, which is precisely the content an AI agent most needs. So over-committing to generation can degrade the docs an agent reads even while making them provably accurate.

### Gaps
- Sources here are practitioner/vendor blogs (Wiz, Zuplo, AppMaster, DocuWriter, dev.to), not peer-reviewed. The causal story is coherent and consistent across them but none reports measured drift rates before/after adopting CI response-vs-spec validation. Treat as practitioner consensus, not evidence.
- Found no usable sources this pass on literate programming (Knuth/`org-babel`/Jupyter-book) drift outcomes, or on measured effects of `sphinx-autodoc` adoption.

## Q3. Assertion/invariant extraction from prose: is anything better than regex, and is it production-grade?

### Takeaway
There is a 19-year research line here (iComment 2007 -> tComment 2012 -> neural JIT detection 2020-2021 -> LLM-based 2024-2026). Its reported numbers are strong only when the target is a *structured, narrow* comment convention (Javadoc `@param`/`@throws` null semantics: ~98% precision), and collapse to F1 in the 0.28-0.65 band on realistic, general, imbalanced corpora. None of the general-purpose detectors is production-grade as an autonomous judge. The single most important finding for the client is the class-imbalance collapse: the best 2026 system loses more than half its precision (0.88 -> 0.39) merely by moving from a 50/50 test split to a realistic 10/90 split.

### Cited Findings
- **iComment** (Tan et al. 2007) first formulated the task, combining NLP, ML and program analysis to extract implicit rules from comments and check them against code; evaluated on Linux, Mozilla, Wine, Apache - [search synthesis, see tComment paper's related work](https://mir.cs.illinois.edu/marinov/publications/TanETAL12tComment.pdf)
- **@tComment** (Tan et al., ICST 2012) tests Javadoc properties about null values and related exceptions. On 5,330 `@param` and 1,770 `@throws` tags, 2,479 properties inferred, it reports overall precision 98/98/100 across its three property classes, recall 99-100, and 99% overall accuracy; free-form text analysis reached 97-100% accuracy *without* NLP. The authors explicitly attribute this to Javadoc API comments being far more structured than C systems comments, with less paraphrase variance. One failure case: precision 50% for *Null Normal* in Xalan, from only two inferred properties - [@tComment PDF](https://mir.cs.illinois.edu/marinov/publications/TanETAL12tComment.pdf); [arXiv 1201.6078](https://arxiv.org/pdf/1201.6078)
- **Deep JIT inconsistency detection** (Panthaplackel, Li, Gligoric, Mooney, AAAI 2021, vol. 35 no. 1, pp. 427-435) frames the task as: given a code change, will the comment become inconsistent? Best model (GRAPH with edit embeddings) reports P 58.5 / R 67.3 / F1 62.6 / Acc 59.9 on the cleaned test sample and P 61.3 / R 71.8 / F1 66.1 / Acc 63.3 on the full test set, averaged over 3 restarts. Their models beat a bag-of-words baseline but **underperform a CodeBERT BOW baseline** - [AAAI version](https://ojs.aaai.org/index.php/AAAI/article/view/16119/15926); [author PDF](https://users.ece.utexas.edu/~gligoric/papers/PanthaplackelETAL21InconsistencyDetection.pdf); [arXiv 2010.01625](https://arxiv.org/abs/2010.01625); code at [panthap2/deep-jit-inconsistency-detection](https://github.com/panthap2/deep-jit-inconsistency-detection)
- Reported CodeBERT-family baselines on this task range from P 67.4 / R 76.8 (BOW) to P 88.4 / R 73.2 (SEQ + features); rule-based @tComment applied to this general corpus is reported at F1 ~66.7 with accuracy ~50 - i.e. the high-precision Javadoc result does not generalize - [search synthesis of the comparison tables](https://people.cs.umass.edu/~brun/class/2024Fall/CS692P/idllm.pdf)
- **C4RLLaMA** is reported to reach F1 91.4% / accuracy 91.8% in the just-in-time setting using a standard diff format, a large jump over the 2021 neural work - [search synthesis](https://people.cs.umass.edu/~brun/class/2024Fall/CS692P/idllm.pdf). Caution: when CASCADE re-ran C4RLLaMA on its own dataset as a baseline it scored P 0.53 / R 0.41 / F1 0.46 (see Q6), so the 91% figure is corpus-specific.
- **DocChecker** (Dau et al. 2023) is an encoder-decoder pre-trained on code-text pairs for post-hoc inconsistency detection, extending Panthaplackel et al. - [arXiv 2306.06347](https://arxiv.org/html/2306.06347v3)
- Reproducibility is poor: to run DocChecker as a baseline, the CASCADE authors had to **re-train the model from scratch and modify lines of its provided library code** - [CASCADE](https://arxiv.org/html/2604.19400)
- Scope limits of the strongest-sounding tools: METAMON and JDOCTOR only handle `@param`, `@return` and `@throws` tags, so they miss inconsistencies expressed anywhere else in a Javadoc block; METAMON's pipeline is bound to Java 8 + JUnit 4 because of its EvoSuite dependency - [CASCADE](https://arxiv.org/html/2604.19400)
- Later work (MCCL, Xu et al.) adds confidence learning, multi-head attention and GNNs plus explicit denoising, motivated by *labeling errors in the training data itself* - [ResearchGate](https://www.researchgate.net/publication/377792240_Code_Comment_Inconsistency_Detection_Based_on_Confidence_Learning)
- Dataset-quality concern is live in this subfield: a 2025 paper asks whether code-comment coherence is even sufficient when optimizing datasets for code summarization - [arXiv 2502.07611](https://arxiv.org/pdf/2502.07611)

### Inferences
- The tComment result is the single most useful data point for the client and is usually misread. Its ~98% precision came from a *narrow, structured, conventional* target with a known vocabulary - not from clever NLP (the paper says it beat iComment's NLP without using NLP). The transferable lesson is not "use an extractor," it is: **precision comes from narrowing the claim schema, not from improving the extractor.** The client's regex-on-named-invariants approach is already in the high-precision regime for the same reason. Replacing regex with a model would trade precision for coverage, which is the wrong direction given an AI-agent consumer that acts confidently on output.
- The right upgrade to regex extraction is therefore *more structure*, not *more intelligence*: register each invariant as a typed claim whose code side is a real symbol reference (import the module, read the attribute) rather than a regex over source text. That converts the check from heuristic-with-good-precision to fully mechanical, and it fails loudly on rename instead of silently matching nothing.
- Nothing in this line is production-grade as an autonomous gate. The cross-corpus instability (C4RLLaMA 91% on one corpus, 46% on another; @tComment 98% on Javadoc nulls, ~50% accuracy generally) is the disqualifying pattern.

### Gaps
- Did not find `@tomassetti`-style doc-linting material in this pass; no citation available for it.
- No source found reporting production deployment of any of these detectors at a named organization with retained false-positive statistics.

## Q4. Traceability links: what does mandatory traceability buy, and is there a cheap 80%?

### Takeaway
The literature is candid that traceability's benefits "often go unrealized" and that its cost in rapidly evolving systems is extremely high; adoption outside regulated domains is driven by perceived benefit, and that perception has *declined* (80% -> 57% citing expected benefit across two studies). The concrete, reusable payoff is change-impact analysis and coverage analysis. The cheap 80% version is a stable, machine-checkable ID in both directions, where the *link check* (does this ID still resolve on both ends?) is mechanical and the *semantic check* is not.

### Cited Findings
- Traceability is a required component of approval/certification in most safety-critical domains, but "the cost, effort, and discipline needed to create and maintain trace links in rapidly evolving systems can be extremely high," and benefits often go unrealized due to ill-defined ad-hoc processes, poor training, or lack of tool support - [Empirical studies in software and systems traceability, EMSE](https://link.springer.com/article/10.1007/s10664-017-9509-1)
- "Why don't we trace? A study on the barriers to software traceability" found expected benefit and mandate were the prevalent adoption reasons at 57% and 48%, with the benefit rationale having **decreased considerably** from an earlier study where 80% cited it. Expected benefit was more common in non-agile paradigms (68.7% vs 51.6%) - [Requirements Engineering journal](https://link.springer.com/article/10.1007/s00766-023-00408-9)
- The practitioner divide: high-end users believe traceability delivers more than it costs, while low-end users acknowledge its importance but treat it as expensive overhead - [Torkar et al. systematic review](https://torkar.github.io/pdfs/00-SUBMITTED-PAPER.pdf)
- The recognized benefit ledger is specifically: change impact analysis (trace links reveal dependent artifacts), coverage analysis (demonstrating no requirement is overlooked), and project status analysis. DO-178C, ISO 26262 and IEC 61508 all require critical-requirement verification be demonstrated through traceability, making the cost non-discretionary in certified domains - [search synthesis of review literature](https://torkar.github.io/pdfs/00-SUBMITTED-PAPER.pdf); [Wikipedia: Requirements traceability](https://en.wikipedia.org/wiki/Requirements_traceability)
- Tailoring trace capture and usage to project-specific needs is argued to be a *prerequisite* for a positive cost-benefit ratio - [Torkar et al.](https://torkar.github.io/pdfs/00-SUBMITTED-PAPER.pdf)
- Jalali and Wohlin's systematic review is reported to find only **moderate** evidence that traceability improves software quality, with effect size heavily dependent on tool support and process maturity - [search synthesis](https://torkar.github.io/pdfs/00-SUBMITTED-PAPER.pdf). Flagging this as a secondary attribution I could not verify against the primary paper.
- Companies studied in a cross-domain RE study cited traceability as a key capability at all sites but "struggle to find the right cost-benefit level" - [Design Society](https://www.designsociety.org/download-publication/40499/EMPIRICAL+STUDY+OF+REQUIREMENTS+ENGINEERING+IN+CROSS+DOMAIN+DEVELOPMENT)
- Adjacent and directly relevant to agent-maintained repos: a 2026 cross-model empirical study on citation discipline in spec-driven development, examining output determinism and automated hallucination detection in LLM-generated code - [arXiv 2606.30689](https://arxiv.org/pdf/2606.30689)

### Inferences
- What mandatory traceability actually buys, stripped of certification theater, is a *queryable bidirectional index*: given a code change, which specs are implicated; given a spec, is anything implementing it. For an AI-agent-maintained repo this is exactly the query an agent needs before editing, and the client's consistency engine already approximates one side of it via path-token extraction from spec prose.
- The cheap 80% is `# implements: SPEC-042`-style markers, but the value split matters: the *resolution* check ("does SPEC-042 exist? does SPEC-042 have at least one implementer?") is mechanical, cheap, and catches deletions and renames. The *correctness* check ("does this code still do what SPEC-042 says?") is not mechanical at all and no marker scheme provides it. Selling `// implements:` as drift detection oversells it; selling it as an impact-analysis index is accurate.
- Coverage analysis is the underrated half. "Spec 002 has zero code referencing it" is a mechanically provable, high-signal finding, and it is exactly the class of finding the client's own ARCHITECTURE.md records having hit manually (ADR-0006 pointing at an architecture - Qdrant/PostgreSQL/MinIO - that nothing implements). A mechanical orphan-spec check would have surfaced that without human reading.
- The declining perceived-benefit trend (80% -> 57%) plus "moderate evidence" for quality effects is the strongest available warning against building heavy traceability machinery. The literature says the ROI is real only with strong tool support - which, for an agent-maintained repo, means the links must be generated and checked by tooling, never hand-maintained.

### Gaps
- No hard quantitative ROI data found (e.g. measured effort-hours saved per maintained trace link). The literature is dominated by perception surveys and interviews. Ahn & Chong's explicit cost-benefit analysis and DO-178C certification-effort measurements were identified as the next step but not retrieved.
- No source found on measured outcomes of lightweight ADR-to-code linking specifically.

## Q5. Structural/graph approaches, and architecture-as-test (import-linter, ArchUnit, pytest-archon)

### Takeaway
This is the strongest *mechanical* answer to architectural claims, and it is the closest existing thing to mechanically-verified architecture documentation: an import-linter contract or ArchUnit rule is a machine-checked assertion about structure that fails the build when reality diverges. The critical honesty caveat is that the evidence base is practitioner consensus and example repositories, not controlled studies, and the tools measure what is easy to measure (static structure) rather than everything a doc claims. For a Python repo the mature options are `import-linter` (CLI, config-driven) and `pytest-archon` / `PyTestArch` (rules as pytest tests).

### Cited Findings
- **import-linter** analyses imports between all modules in one or more packages and compares them against declarative "contracts" in a config file; it builds an import graph and each contract checks whether any edge violates it. It also ships a browser UI for exploring a package's architecture - [Import Linter docs](https://import-linter.readthedocs.io/); [Overview](https://import-linter.readthedocs.io/en/v2.7/readme.html)
- Contract types: **forbidden** (prevent one set of modules importing another), **protected** (no direct imports except from an allow-list), **layers** (enforce high-to-low dependency direction), **independence** (a set of modules must not depend on each other), **acyclic siblings** (forbid cycles between siblings), plus **custom contract types** - [Contract types](https://import-linter.readthedocs.io/en/latest/contract_types.html)
- Layers semantics are transitive and apply to all nested modules: `mypackage.low.one` may not import `mypackage.high.two`. Refinements that matter for adoption: **containers** (less repetitive layer specs), **optional layers** (parenthesized, so a missing layer does not break the contract), **exhaustive mode** (every module in each container must be declared as a layer, so adding a new module flags the contract - only supported for layers with containers), **multi-item layers** via `|`, and **cross-package layering** treating each top-level package as a layer - [Layers docs](https://import-linter.readthedocs.io/en/v2.9/contract_types/layers/)
- Failure output reports **full import chains**, e.g. `myproject.foo.blue -> myproject.utils.red (l.16)` then `myproject.utils.red -> myproject.utils.green` then `myproject.utils.green -> myproject.bar.yellow` - so it surfaces indirect coupling, not just direct imports. This is what makes it usable as a CI gate - [Import Linter docs](https://import-linter.readthedocs.io/)
- Incremental adoption is explicit: `ignore_imports` grandfathers known violations (e.g. `ignore_imports = mypackage.bar.green -> mypackage.utils`) so teams ratchet rather than big-bang. Config can live in `pyproject.toml` via `[tool.importlinter]` / `[[tool.importlinter.contracts]]`, and a programmatic API exists (`from importlinter import api`, `api.read_configuration()`) - [Import Linter docs](https://import-linter.readthedocs.io/); [Contract types](https://import-linter.readthedocs.io/en/latest/contract_types.html)
- Typical stated motivation: utility functions should not depend on specificities of the project - [Roman Imankulov, "Linter for Python Architecture"](https://roman.pt/posts/python-architecture-linter/)
- **pytest-archon** defines architectural boundaries ("forbidden dependencies") as ordinary pytest test cases runnable in CI. API example: `archrule("protect the domain model").match("app.domain_model*").should_not_import("app*").may_import("app.domain_model*").check("app")`. Matching is fnmatch by default, regex via `use_regex=True`. By default the whole file is scanned so imports inside functions/methods are found and **transitive dependencies are checked**; `only_toplevel_imports=True` ignores conditional/function-local imports; `skip_type_checking=True` skips `if typing.TYPE_CHECKING` blocks - [jwbargsten/pytest-archon](https://github.com/jwbargsten/pytest-archon); [Xebia: How to tame your Python codebase](https://xebia.com/blog/how-to-tame-your-python-codebase/)
- Concrete adoption report: a 160k-line Django project codified architectural rules as pytest-archon tests, and wired them into AI-editor verification prompts - run the architecture tests, fix violations, do not modify the test files, re-run until green - [Medium: Testing Architectural Integrity with pytest-archon](https://medium.com/@eamonn.faherty_58176/keeping-your-django-codebase-in-line-testing-architectural-integrity-with-pytest-archon-7ddc208d28ad)
- **PyTestArch** is an alternative with a more verbose fluent API: build an evaluable representation via `get_evaluable_architecture(...)`, then `Rule().modules_that().are_named(...).should_not().be_imported_by_modules_that().are_sub_modules_of(...)`. It scans imports, builds an internal graph, and answers rule queries - [PyTestArch on PyPI](https://pypi.org/project/PyTestArch/); [Enforcing Python Architecture Rules with PyTestArch](https://andi-john-dev.de/blog/python-architecture-rules-with-pytestarch)
- **ArchUnitPython** supports rules like `project_files("src/").should().have_no_cycles()` with `assert_passes(rule)`, and itself positions CLI-first tools **Tach** and **Import Linter** as adjacent alternatives - [LukasNiessen/ArchUnitPython](https://github.com/LukasNiessen/ArchUnitPython)
- **ArchUnit** (Java) enforces structure as JUnit assertions: package structure, package/class dependencies, flow between layers, circular dependencies. It reads `.class` files on the test classpath, so it sees compiler-resolved dependencies including implicit ones, and a violation surfaces as an ordinary failing test - [loiane.com: Architecture Testing for Java with ArchUnit](https://loiane.com/2026/07/architecture-testing-java-archunit/)
- ArchUnit's `FreezingArchRule` exists specifically to baseline existing violations for incremental adoption on legacy code - [loiane.com](https://loiane.com/2026/07/architecture-testing-java-archunit/)
- The fitness-function framing comes from Ford and Parsons, *Building Evolutionary Architectures*: a fitness function is any mechanism giving an objective integrity assessment of some architectural characteristic, expressed as an executable test - [Mikael Vesavuori: Up-and-Running Guide to Architectural Fitness Functions](https://mikaelvesavuori.se/blog/2023-08-20_The-Up-and-Running-Guide-to-Architectural-Fitness-Function); [Lukas Niessen: Fitness Functions](https://lukasniessen.medium.com/fitness-functions-automating-your-architecture-decisions-08b2fe4e5f34)
- **Two honest caveats, both sourced.** (1) Evidence is practitioner reports, blogs, and example repos, not controlled studies; the strongest concrete anecdote is a consultant whose pipeline failed after a junior developer injected a cross-domain repository call, which "might have grown roots" without the check. The comparative claim ("a reviewer catches it only if they know the rule and are paying attention; the test catches it every time") is an argument about determinism, not a measured outcome. (2) There is a known **selection bias toward structural characteristics**: because code is tangible and test frameworks favor atomic tests, it is tempting to define fitness functions on code structure - i.e. these tools measure what is easy to measure. Genuine coverage also needs dynamic functions (p99 latency, bounded memory, business invariants) - [Ben Morris: Using architectural fitness functions](https://www.ben-morris.com/using-architectural-fitness-functions-as-a-guide-to-system-design/); [dev.to: Modular Monolith 2026 Guide](https://dev.to/x4nent/the-modular-monolith-2026-complete-guide-spring-modulith-archunit-fitness-functions-and-lessons-878)
- Escape hatches are argued to be necessary, not optional: a fitness function should not block without one; track exemptions and review them periodically, or teams route around the checks entirely - [dev.to: Modular Monolith 2026 Guide](https://dev.to/x4nent/the-modular-monolith-2026-complete-guide-spring-modulith-archunit-fitness-functions-and-lessons-878)
- Runnable example rule sets exist, including one deliberately designed so that all fitness functions fail, to demonstrate violation reporting - [thmuch/architecture-fitness-functions](https://github.com/thmuch/architecture-fitness-functions); [sann3/architecture-fitness-function-examples](https://github.com/sann3/architecture-fitness-function-examples)

### Inferences
- This is the answer to "this doc says A calls B; does A still call B?" - but with an important inversion. These tools do not *read the doc and check it*; they *replace the doc's structural claims with the check*. The doc becomes a rendering of the contract file rather than an independent prose assertion. That inversion is what makes it mechanical, and it is also its cost: you must be willing to move architectural claims out of prose and into a contract file.
- Import graphs prove *absence of dependency* far better than *presence of behavior*. "domain must not import infrastructure" is fully provable. "A calls B" is only provable at import granularity, and "the pipeline is walk -> parse -> chunk -> embed" is not provable at all by an import linter - ordering and call sequence need a call graph, and even then dynamic dispatch defeats static analysis in Python.
- `import-linter`'s **exhaustive mode** is the highest-leverage single feature for an agent-maintained repo and is directly relevant to the client: it fails when a *new* module appears that is not declared in the contract. That is a mechanical guard against the exact drift pattern where an agent adds `src/holusight/new_thing.py` and the module inventory in `AGENTS.md`/`ARCHITECTURE.md`/`.claude/rules/structure.md` silently falls behind. The same idea generalizes: a mechanical "every file on disk is accounted for in the structure doc, and every doc entry resolves to a file" bidirectional set-equality check.
- The client's repository already maintains three overlapping hand-written module inventories (`AGENTS.md`, `ARCHITECTURE.md`, `.claude/rules/structure.md`). Set-equality against the filesystem is mechanically provable, near-zero maintenance, and directly protects an agent from being told a module exists that does not, or from missing one that does. This is the cheapest concrete win visible in this survey.
- CodeQL / Semgrep / Sourcegraph / Glean / Kythe are real and powerful, but I found no sourced evidence in this pass of anyone using them to verify *documentation* claims. Semgrep/CodeQL are practical for encoding a specific invariant as a pattern query (e.g. "no write call under an indexed path"), which is the security-invariant class rather than the architecture-doc class. The report should not assert doc-verification adoption for these.

### Gaps
- No download/adoption statistics retrieved for import-linter, pytest-archon or PyTestArch (PyPI download counts would settle relative adoption; not fetched).
- No controlled study found on whether architecture-as-test reduces architecture erosion. The absence is itself a finding and should be stated.
- Tach was named only as an adjacent alternative; not investigated.
- No sourced example found of a code graph being used to verify a natural-language architecture description. If the report wants to claim this is a gap in the market, that claim is supported by absence of evidence, not by a source.

## Q6. LLM-based consistency checking: accuracy, false-positive rates, and LLM-as-ranker

### Takeaway
This is where the sharpest and most decision-relevant 2025-2026 evidence lives, and it says something the client will like: **naive LLM prompting flags over 90% of functions as inconsistent and is therefore useless as a gate**, and the systems that fix this do so by *narrowing the question*, not by using a better model. DocPrism gets flag rate down to 17% with precision 0.63 by asking only about *incorrectness* (contradiction) and discarding *incompleteness*. CASCADE gets precision 0.88 by requiring an executable test to discriminate, but at recall 0.21 - and its precision falls to 0.39 on a realistic 10/90 class balance.

### Cited Findings
- **DocPrism** (Xu, Wahab, Holmes, Lemieux; ISSTA 2026, DOI 10.1145/3832248) covers **Python, TypeScript, C++ and Java**, with no fine-tuning. Reported: **precision 0.63** across four languages; **0.47-0.67 on a real-world Java dataset versus state-of-the-art's 0.05-0.14**; **overall flag rate 17%**; **F1 0.77 after applying its LCEF methodology, up from 0.22 with standard prompting**. It establishes that inconsistency errors exist in at least **11%** of code-documentation pairs across those languages - [arXiv 2511.00215](https://arxiv.org/abs/2511.00215)
- DocPrism's stated core problem with the naive approach: **standard LLM prompting yields "unacceptably high inconsistency flag rates - i.e., over 90% of functions are flagged,"** because LLMs conflate high-level documentation with detailed code and report the gap as an inconsistency - [arXiv 2511.00215](https://arxiv.org/abs/2511.00215)
- DocPrism's mechanism, **LCEF (Local Categorization, External Filtering)**, "uses an LLM's local completion skills, rather than its long-term reasoning skills, to focus on reporting incorrectness inconsistencies." The key design decision is in the title: target *incorrectness* inconsistencies, not all gaps - [arXiv 2511.00215](https://arxiv.org/abs/2511.00215)
- DocPrism reportedly generates prompts per function/documentation pair fed to **LLaMA 3.1-70B at temperature 0**, outputting JSON; in about **3.7% of evaluated pairs the output does not match the schema**, so no inconsistencies are reported for those - [search synthesis citing DocPrism](https://arxiv.org/pdf/2511.00215). Flagging a conflict: the abstract fetch did not name a model, so the specific model attribution is from a secondary summary and should be checked before being asserted.
- **CASCADE** (arXiv 2604.19400) generates unit tests from natural-language documentation and reports an inconsistency only when **the existing code fails a test while code generated from the documentation passes the same test** - a dual-verification design explicitly aimed at minimizing false positives. Dataset: **71 inconsistent and 814 consistent** code-documentation pairs from open-source Java projects, plus additional testing on Java, C# and Rust repos. All LLMs run at temperature 0 with **gpt-4.1-mini** - [arXiv 2604.19400 HTML](https://arxiv.org/html/2604.19400); [PDF](https://arxiv.org/pdf/2604.19400)
- CASCADE's numbers, **on a balanced 50/50 split**: precision 0.88, recall 0.21, F1 0.35, specificity 0.97, pair-wise fix precision 0.87. **On the realistic 10/90 split**: precision **0.39**, recall 0.21, F1 0.28. Baselines on the 50/50 split: best LLM-baseline (LLM-Ac) P 0.55 / R 0.46 / F1 0.50; DocChecker-single P 0.49 / R 0.96 / F1 0.65; C4RLLaMA-single P 0.53 / R 0.41 / F1 0.46 - [arXiv 2604.19400 HTML](https://arxiv.org/html/2604.19400)
- CASCADE's field result: it **uncovered 13 previously unknown inconsistencies, of which 10 were subsequently fixed** - [arXiv 2604.19400](https://arxiv.org/abs/2604.19400)
- CASCADE's own stated limitation: automatic reports still require human confirmation, and "false positives carry serious consequences: wasting developer time and discouraging practical adoption" - [arXiv 2604.19400](https://arxiv.org/abs/2604.19400)
- **METAMON** (Lee et al., LLM4Code @ ICSE 2025) uses EvoSuite search-based test generation to capture current behavior as assertions, then LLM reasoning plus metamorphic relations and self-consistency to find oracles inconsistent with the documented spec. On **9,482 documentation/code pairs from five Defects4J v2.0.1 projects: precision 0.72, recall 0.48** - [arXiv 2502.02794](https://arxiv.org/pdf/2502.02794); [ICSE 2025 LLM4Code listing](https://conf.researchr.org/details/icse-2025/llm4code-2025-papers/18/METAMON-Finding-Inconsistencies-between-Program-Documentation-and-Behavior-using-Met)
- Other 2025-2026 work in the area, for completeness: a dataset for code-documentation alignment, **CoDocBench** (MSR 2025); **Natural Language-Focused SE via Code-Documentation Equivalence** ([arXiv 2606.22247](https://arxiv.org/pdf/2606.22247)); **From Reading Code to Reading Spec: A Verified Layer for LLM-Driven Codebase Maintenance** ([arXiv 2609.06383](https://arxiv.org/pdf/2609.06383)); **Leveraging Structured Code Diffs for Comment** inconsistency work ([arXiv 2512.19883](https://arxiv.org/pdf/2512.19883)); **CCISolver** named as an auto-repair detector - [CASCADE related work](https://arxiv.org/html/2604.19400)
- A directly relevant adjacent finding for agent-maintained repos: **"Articulate but Wrong: Self-Review Failures in LLM-Based Code Modernization"** uses a benign-control set of code needing no modernization, cleanly measuring the baseline rate at which LLMs introduce drift when none is warranted - [arXiv 2605.21537](https://arxiv.org/html/2605.21537)
- Practitioner-side claim in the same direction: automated detectors (METAMON, DocChecker, CCISolver, DocPrism) "can be integrated into CI/CD pipelines to flag or auto-repair inconsistencies at commit or PR time" - [search synthesis](https://www.emergentmind.com/topics/description-code-inconsistency). This is a capability claim, not evidence of deployment.

### Inferences
- The class-imbalance result is the single most important number in this whole survey for the client's decision. CASCADE's precision drops 0.88 -> 0.39 purely from moving 50/50 -> 10/90, with recall unchanged. Any repo-scale nightly check operates at a *far* more extreme imbalance than 10/90 - most doc paragraphs are fine most nights. Extrapolating, a nightly LLM judge over a mid-size repo would produce a majority-false-positive queue. That is not a cost/noise tradeoff an agent-maintained repo can absorb, because the triage labor is exactly what the agent setup is trying to avoid.
- Therefore: **LLM-as-ranker is the defensible use; LLM-as-judge is not.** The evidence supports this indirectly but strongly. DocPrism's entire contribution is a mechanism for *suppressing* reports (17% flag rate vs >90%); CASCADE's is *requiring an executable discriminator* before reporting. Both are, structurally, ways to stop the LLM from being the judge. Neither paper frames itself as a ranker, so the ranker framing is my inference from their designs plus the imbalance numbers - the report should present it as reasoning, not as a cited claim.
- CASCADE's dual-verification design is the most transferable idea here and is *not* LLM-dependent in spirit: generate a test from the doc, run it against the code, and report only when the code fails a test that doc-derived code passes. The LLM is confined to generating a candidate test - a proposal that is then mechanically adjudicated. This is the correct architecture for an agent-run check: **LLM proposes, execution decides.** Cost: recall 0.21, i.e. it finds about a fifth of real inconsistencies. For a repo whose failure mode is "an agent acts confidently on a wrong doc," a low-recall/high-precision detector is the right shape.
- METAMON's P 0.72 / R 0.48 is the best balanced result reported, but it is unusable outside Java 8 + JUnit 4 (see Q3), and its scope is three Javadoc tags. The Python equivalent does not exist as an off-the-shelf tool.
- DocPrism's "at least 11% of code-documentation pairs contain inconsistency errors" is the best available base-rate estimate and covers Python. It is useful for sizing: on a repo with a few hundred documented functions, expect a few dozen genuine inconsistencies, and expect a precision-0.63 detector to hand back roughly one false alarm for every two true ones.

### Gaps
- No per-sample cost figures reported by CASCADE or DocPrism, so nightly-run cost cannot be estimated from sources.
- No false-positive *rate* (as opposed to precision and flag rate) reported by CASCADE.
- DocPrism's model attribution conflicts between sources (abstract unspecified vs secondary summary saying LLaMA 3.1-70B); unresolved.
- Several cited arXiv IDs are 2026 preprints (2604.19400, 2605.21537, 2606.22247, 2606.30689, 2609.06383, 2512.19883). CASCADE's numbers were read from its own HTML and are solid; the others are known only from search summaries and abstracts and should be verified before being quoted in detail.
- Found no study measuring precision of LLM doc-drift checking on *architecture-level prose* (as opposed to function-level docstrings). All the numbers above are function/docstring granularity. This is a material gap given the client's docs are architecture-level.

## Q7. Process controls: which ones change behavior and which become rubber stamps?

### Takeaway
There is real empirical evidence here and it is discouraging for the weakest controls. Co-evolution studies measure that code and comments do *not* co-evolve in most cases (roughly 20% of the time in the largest study), so any control relying on authors noticing is already known to fail at scale. The controls with evidence behind them are structural: co-location of docs with code (Google's g3doc), named ownership, and automated freshness tooling in CI. Google's own account is that undocumented ownership produced ~90% dead documents.

### Cited Findings
- Fluri et al. (WCRE 2007), "Do code and comments co-evolve?", on ArgoUML, Azureus and JDT Core: **97% of comment changes occur in the same revision as the corresponding source code change**, but only **23% / 52% / 43%** of all comment changes (per project) were *triggered by* source code changes. Newly added code is scarcely commented, and when commented it is mostly class and method declarations. Methodological caveat reported by the authors: comment-to-comment changes are double-counted, giving a 4-10% error rate - [search synthesis of Fluri et al. 2007, WCRE, pp. 70-79](https://www.researchgate.net/publication/4297140_Do_Code_and_Comments_Co-Evolve_On_the_Relation_between_Source_Code_and_Comment_Changes)
- Fluri et al. (Software Quality Journal 17, 2009, pp. 367-394), eight systems: comment-to-code proportion increases similarly across all eight, newly added code is not consistently well-commented, and in **six of eight systems comments and their associated code changes co-evolve in more than 90% of comment changes** - [ResearchGate](https://www.researchgate.net/publication/220635933_Analyzing_the_co-evolution_of_comments_and_source_code)
- **The crucial reinterpretation:** those 90-97% figures are conditional on a comment change happening at all - they are not a measure of how often stale comments get updated. Comment change is triggered by the respective code change in **less than half** of code-change cases, and for some projects up to **10% of comment changes happen more than 3 revisions later** - [Wen et al., ICPC 2019](https://www.inf.usi.ch/lanza/Downloads/Wen2019a.pdf)
- **Wen et al. (ICPC 2019)**, large-scale study of code changes in **1,500 projects** plus manual analysis of **500 commits**: in most cases code and comments do **not** co-evolve simultaneously, with co-evolution occurring roughly **20%** of the time - [A Large-Scale Empirical Study on Code-Comment Inconsistencies](https://www.inf.usi.ch/lanza/Downloads/Wen2019a.pdf); [ACM](https://dl.acm.org/doi/abs/10.1109/ICPC.2019.00019)
- Class-comment replication: on a 15% sample of 327 classes where both comment and code changed, **50% of class-comment changes were related to code changes and 50% were not**, even though 73% of the code changes in those classes added, updated or removed methods - [Rani et al.](https://scg.unibe.ch/archive/papers/Rani21b.pdf)
- **Google's account (Software Engineering at Google, ch. 10)**: the most successful documentation efforts came from treating documentation like code - under source control, with clear ownership, reviewed on change, issues tracked as bugs, periodically evaluated/tested, and measured for accuracy and freshness where possible. Explicit caveat in the book: Google has internally developed tools to "test" documentation freshness and accuracy, and **public tools have still not caught up in that domain** - [abseil.io SWE book ch.10](https://abseil.io/resources/swe-book/html/ch10.html)
- **Ownership is presented as the antidote to staleness**: "documents without owners become stale and difficult to maintain," and canonical documentation must be designated where documents conflict, with duplicates consolidated or deprecated - [abseil.io ch.10](https://abseil.io/resources/swe-book/html/ch10.html)
- **The measured failure of the ownerless wiki**: when GooWiki was deprecated, **around 90% of the documents had no views or updates in the previous few months** - [abseil.io ch.10](https://abseil.io/resources/swe-book/html/ch10.html)
- **Freshness dates**: Google attaches freshness dates noting when a document was last reviewed; metadata sends email reminders when a document has not been touched in, for example, three months, and **freshness is examined through an internal tool baked into CI** - [abseil.io ch.10](https://abseil.io/resources/swe-book/html/ch10.html)
- **g3doc / co-location**: Google embedded documentation within the code repository so engineers update code and its docs in the same change, with docs predictably located next to the source rather than "off in an unfindable document or webpage." This made doc maintenance the same experience as code maintenance (bugs, changelists, expert review) - [abseil.io ch.10](https://abseil.io/resources/swe-book/html/ch10.html); [abseil.io ch.3, Knowledge Sharing](https://abseil.io/resources/swe-book/html/ch03.html)
- Community upkeep increased notably with g3doc: engineers felt empowered to update documentation regardless of ownership, because it was easy to find an owner to review a suggestion and the change history was auditable like code's - [abseil.io ch.3](https://abseil.io/resources/swe-book/html/ch03.html)
- The measured motivation for the g3doc investment: **48% of Google engineers cited docs as their #1 productivity issue (Googlegeist 2014)**, and **over 50% of SRE issues cited problems with docs**; the strategy was to fix culture bottom-up and tooling top-down - [MacNamara, SREcon16 Europe, "The Knowledge"](https://www.usenix.org/sites/default/files/conference/protected-files/srecon16europe_slides_macnamara.pdf); see also [Seeking SRE ch.19](https://www.oreilly.com/library/view/seeking-sre/9781491978856/ch19.html)
- Deprecation is treated as a first-class requirement: when a document no longer serves a purpose, remove it or mark it obsolete and point to the replacement - [abseil.io ch.10](https://abseil.io/resources/swe-book/html/ch10.html)
- **A mechanical CI control with published field results**: the DOCER line. Extract candidate code-element references from README and wiki prose with regular expressions, count whole-word, case-sensitive, exact-match instances in source at two revisions (the revision when the doc was last updated, and current HEAD), and flag when the count goes from positive to zero. **28.9% of the top 1,000 most popular GitHub projects contain at least one outdated reference to source code in their documentation**; over 3,000 projects analysed, most contain at least one outdated reference at some point in their history. Inter-annotator agreement on true positives was free-marginal kappa 0.92 on 50 randomly selected code elements - [Tan, Wagner, Treude, Empirical Software Engineering 29(1):5, 2023](https://link.springer.com/article/10.1007/s10664-023-10397-6); [arXiv 2212.01479](https://arxiv.org/pdf/2212.01479)
- DOCER's **known false-positive sources**, stated by the authors: deleting the final instance of a code element that only appears in a source comment; **change logs**, which reference removed elements precisely to signal deprecation and produce false positives that are "hard to eliminate and require individual maintainer verification"; and file-path references, handled by treating each path variant matching a reference as an additional instance - [EMSE](https://link.springer.com/article/10.1007/s10664-023-10397-6)
- The follow-up **DOCER TOOL** ships as a **GitHub Action that runs on every pull request**. Stated limitations: it only covers GitHub READMEs and wiki pages (not externally hosted docs), and the regular expressions have not been validated across all programming languages. GitHub issues were filed against real projects and some led to documentation fixes - [arXiv 2307.04291](https://arxiv.org/pdf/2307.04291)
- Note on naming: **DocRef** (Zhong and Su, "Detecting API documentation errors") is separate earlier work using island parsing, not the same as DOCER - [ACM](https://dl.acm.org/doi/10.1145/2544173.2509523)
- Transferable process point from the API-drift literature: ship spec changes in the same PR, because separating code review from contract review recreates drift "just with better tooling" - [AppMaster](https://appmaster.io/blog/openapi-first-vs-code-first-api-development)

### Inferences
- The Wen et al. ~20% co-evolution rate is the empirical death of "docs-in-the-same-PR" as a *convention*. As a convention relying on author diligence, it is measured to fail roughly four times in five. It only works when a mechanical check forces it, which is the DOCER-as-GitHub-Action shape or the OpenAPI-diff-in-CI shape.
- Google's evidence separates cleanly into two kinds. The behavior-changing controls are **structural**: co-location (g3doc), named ownership, and freshness tooling in CI. The rubber-stamp risk sits with **time-based freshness reminders** - a "reviewed on" date can be bumped without reading anything, and Google's own framing (email reminders when untouched for three months) is explicitly a prompt, not a verification. The report should say this directly: freshness dates measure *attention*, not *accuracy*, and are trivially gameable, most of all by an agent that can bump a date field.
- CODEOWNERS on doc paths and required doc review were not found in any empirical source in this pass. Mechanistically they are the "clear ownership" control Google credits, but I have no measurement of their effect and should not imply one.
- **DOCER is the most under-appreciated result in this survey for the client's exact situation.** It is nearly free, fully mechanical in its core check (symbol exists / symbol does not exist), needs no model, needs no training corpus, and has a published base rate showing 28.9% of top GitHub projects are already failing it. It is strictly an upgrade path over content-hash diffing: hash diffing says "something changed," DOCER says "this named thing in the doc no longer exists in the code," which is directly actionable and near-zero false-positive once change-log files are excluded.
- The client's repo already does a variant of this (`exact` provider, path-token extraction with DANGLING_REFERENCE flagging) and has already hit DOCER's exact documented false-positive class: illustrative/fictional paths in research prose (specs 011/012) surfacing as dangling references. DOCER's authors report the same problem shape with change logs. The known-good mitigation is scoping: exclude change-log and research-prose regions rather than trying to improve the extractor. This is worth calling out because it means the client's limitation is a *documented, expected* limitation of a technique with published field results, not a flaw in their implementation.

### Gaps
- No empirical evidence found on CODEOWNERS-on-docs, required doc review, or CI checks that fail when code changes without a doc change (as opposed to checks that verify a specific claim). Treat all of these as unevidenced.
- Google's internal freshness/accuracy tooling is described but not specified; the book explicitly notes public tools have not caught up, so no implementation detail is available.
- GitLab handbook practices, Stripe and Sourcegraph engineering writing were listed as suggested sources but not retrieved in this pass.
- No measurement found of whether freshness dates are in practice bumped without review (the rubber-stamp hypothesis is mechanistically obvious but unmeasured).

## Q8. Synthesis: highest-leverage next technique given hash-diffing plus regex invariants

### Takeaway
The highest-leverage next technique is **mechanical bidirectional reference checking - name-level, symbol-resolved, set-complete - not a smarter judge of prose.** Specifically: every code element named in a doc must resolve to a real symbol/file in the current tree, and every module/file on disk must be accounted for in the structure documents. This is the DOCER result (28.9% of top-1000 GitHub projects already fail the one-directional version) combined with import-linter's exhaustive mode (fails when an undeclared module appears). It is fully mechanical, model-free, near-zero maintenance, and it closes the exact gap hash-diffing leaves: hash-diffing says "both changed," reference checking says "the doc names something that does not exist."

### Cited Findings
Supporting evidence is assembled from the preceding sections; the load-bearing citations are repeated here for the writer's convenience.

- 28.9% of the top 1,000 most popular GitHub projects contain at least one outdated code-element reference in their documentation; the check is exact-match instance counting across two revisions, no model involved - [EMSE 29(1):5](https://link.springer.com/article/10.1007/s10664-023-10397-6)
- The check already ships as a per-pull-request GitHub Action - [arXiv 2307.04291](https://arxiv.org/pdf/2307.04291)
- import-linter's exhaustive mode causes a contract to flag when any new module appears in a container that is not declared as a layer - i.e. mechanical detection of undeclared additions - [Layers docs](https://import-linter.readthedocs.io/en/v2.9/contract_types/layers/)
- Code and comments do not co-evolve in ~80% of cases (1,500 projects, 500 manually analysed commits), so conventions relying on author diligence are measured to fail - [Wen et al., ICPC 2019](https://www.inf.usi.ch/lanza/Downloads/Wen2019a.pdf)
- Naive LLM doc-consistency prompting flags over 90% of functions; the fix is narrowing the question, and even the narrowed version lands at precision 0.63 / flag rate 17% - [DocPrism, arXiv 2511.00215](https://arxiv.org/abs/2511.00215)
- The highest-precision LLM system available (CASCADE) falls from precision 0.88 to 0.39 purely by moving from a 50/50 to a 10/90 class balance, at recall 0.21 throughout - [arXiv 2604.19400](https://arxiv.org/html/2604.19400)
- The one durable high-precision result in the extraction literature (@tComment, ~98% precision) came from narrowing to a structured convention, and the authors attribute it to that structure rather than to technique - [@tComment](https://mir.cs.illinois.edu/marinov/publications/TanETAL12tComment.pdf)
- Google, which built internal doc freshness/accuracy testing, reports that public tooling in this area has still not caught up, and that its durable wins were co-location, ownership and CI-integrated freshness - [abseil.io SWE book ch.10](https://abseil.io/resources/swe-book/html/ch10.html)

### Inferences

**Ordered by real-world leverage for a mid-size Python repo maintained by agents.**

1. **Bidirectional mechanical reference/inventory checking.** Doc -> code: every named symbol, module, path, CLI flag, env var and config key in a doc resolves in the current tree (DOCER's result; exclude change-log and illustrative-prose regions, which its authors document as the irreducible false-positive class). Code -> doc: set-equality between files on disk and the entries in the structure documents, i.e. import-linter's exhaustive-mode idea generalised. Cost: one script plus an exclusion list; maintenance is the exclusion list only. Proves: named things exist and the inventory is complete. Cannot prove: that any prose statement about behavior is true.
2. **Typed-symbol invariant assertions replacing regex invariants.** Import the module and read the attribute instead of regexing the source; assert doc-stated value == live value. Converts the client's existing heuristic into mechanical verification and makes renames fail loudly instead of silently matching nothing. Cost: one test per invariant, roughly a line each.
3. **Architecture-as-test via import-linter (layers/forbidden/independence, with `ignore_imports` to ratchet).** This is the only mechanism in the survey that mechanically verifies an architectural claim. Cost: a contract file plus periodic exemption review; the sourced warning is that without escape hatches teams route around it. Proves: absence of forbidden dependencies, transitively, with full import chains in the failure output. Cannot prove: call ordering, pipeline sequence, runtime behavior, or anything about dynamic dispatch.
4. **Executable documentation (Sybil or pytest-codeblock over docs and specs).** Proves every fenced Python example still runs. Cost: a `conftest.py` and CI wiring. Ceiling: only covers behavioral, self-contained, deterministic examples - a small fraction of architecture-level prose.
5. **Generation plus CI diff for any doc surface derivable from code.** The client already runs this pattern for the generated skill file with a drift test; the leverage is in extending it, not inventing it. Proves: the generated projection matches its source. Relocates drift into whatever feeds the generator.
6. **LLM as a *ranker of suspicion*, gated by execution where possible, never as a judge.** The defensible shapes are CASCADE's (LLM proposes a test, execution adjudicates) and DocPrism's (LLM answers a deliberately narrowed incorrectness question, with external filtering). Expect low recall by construction, and budget explicit human-or-authorised-agent triage. Cost: per-run inference plus ongoing triage, which is the expensive part and the part that does not amortise.
7. **Process controls.** Co-location and ownership have the best evidence (Google). Docs-in-the-same-PR is measured to fail as a convention and only works when mechanically enforced. CODEOWNERS-on-docs and required doc review are unevidenced either way.

**Most oversold, in order:**

- **LLM-judge nightly doc-consistency checking.** The imbalance collapse (0.88 -> 0.39 precision on a 10/90 split, with real repos far more imbalanced than 10/90) plus the >90% naive flag rate means the default outcome is an alarm queue that is majority noise. It is sold as "just add an LLM pass"; the papers that make it work are papers about *how hard it is to stop the LLM from flagging everything*.
- **Freshness dates and review timestamps.** They measure attention, not accuracy, and an agent can bump a date without reading anything. Google uses them as reminders alongside real CI tooling, not as verification, and the report should not let the "Google does freshness dates" line imply more than that.
- **Heavyweight traceability.** The literature's own numbers (perceived benefit falling 80% -> 57%; only "moderate" evidence for quality effects; benefits "often go unrealized") argue against building machinery. The cheap 80% - a resolvable ID checked mechanically in both directions, used as an impact-analysis index - captures most of the value. Claiming `// implements: SPEC-042` detects drift is the oversell; it detects *deletion and orphaning*, which is still worth having.
- **Architecture fitness functions as a complete answer.** Sourced caution: these tools measure what is easy to measure (static structure) and there is a known selection bias toward it; genuine coverage needs dynamic functions too. They also do not verify prose - they replace it.
- **"Docs as code" as a slogan.** The parts with evidence are co-location, ownership, and CI-integrated checking. The slogan is often used to mean "put Markdown in git," which by itself is the GooWiki outcome with better version control.

**One framing worth handing to the client, supported by the pattern across every section:** every technique that achieved high precision did so by *narrowing what it claims to check*, never by getting smarter. @tComment narrowed to a Javadoc tag convention (98%). CASCADE narrowed to executable discrimination (0.88 on balanced data). DocPrism narrowed to incorrectness-only (flag rate 90%+ -> 17%). import-linter narrowed to import edges (mechanical). The client's regex-on-named-invariants is already an instance of the winning pattern. The next move is to narrow further and *resolve symbols instead of matching strings*, not to widen coverage with a model.

### Gaps
- No source directly compares these techniques head-to-head on the same repository, so the ordering above is my synthesis from per-technique evidence, not a measured ranking.
- No cost data (CI minutes, inference spend) from any source, so relative cost claims are structural arguments only.
- The specific claim that agents are more harmed by stale docs than humans are - the client's premise - is not directly evidenced by anything found. The closest support is [arXiv 2605.21537](https://arxiv.org/html/2605.21537) measuring the baseline rate at which LLMs introduce unwarranted drift during modernization, and the general finding that LLMs conflate documentation-level and code-level detail ([DocPrism](https://arxiv.org/abs/2511.00215)). The premise is plausible and widely assumed but I found no study measuring agent task success as a function of documentation accuracy. This is the most important open question in the whole survey and the report should say so.
